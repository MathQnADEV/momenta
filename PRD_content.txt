Ruang Lingkup Dokumen IniDokumen PRD sebelumnya (“Fitur Foto Kenangan (Photo Booth) pada PSD”) sudah menetapkan kebutuhan produk: latar belakang, tujuan, alur pengguna, kebutuhan fungsional/non-fungsional, dan pertanyaan terbuka. Dokumen itu tidak diulang di sini kecuali diperlukan untuk konteks.Dokumen ini adalah turunannya yang berfokus pada satu keputusan yang diminta secara eksplisit: implementasi ditulis dalam Laravel murni — Blade (PHP + HTML dalam satu file) dan JavaScript vanilla di sisi klien, tanpa lapisan SPA terpisah (Inertia/Vue) atau framework reaktif tambahan (Livewire/Alpine). Isinya adalah struktur proyek, skema data final, kontrak API, potongan kode kunci, rencana pengujian, dan tahapan pengembangan — cukup rinci untuk langsung dieksekusi oleh developer yang menulis kode.1. Keputusan Arsitektur1.1 Perubahan dari PRD SebelumnyaAspekPRD Produk (usulan awal)PRD Teknis ini (final)FrontendInertia.js + Vue 3 (alternatif: Livewire + Alpine.js)Blade + JavaScript vanilla (ES modules)Build toolingPerlu Vite + build step komponen VueVite tetap dipakai, tapi hanya untuk bundling JS/CSS biasa — tidak ada komponen frameworkState UI (countdown, progres pose, posisi stiker)Reactive state Vue (ref/reactive)Objek state JS biasa + manipulasi DOM langsung, mengikuti pola yang sudah ada di prototipeAlasanDianggap paling umum untuk interaksi “banyak state berubah cepat”Diminta pemilik produk: satu project Laravel, PHP dan HTML menyatu di Blade, tanpa lapisan SPA tambahanCatatan tingkat keyakinan: Sedang. Pendekatan Blade + vanilla JS valid secara teknis dan justru paling dekat dengan prototipe yang sudah divalidasi (psd_photobooth_prototype.html juga vanilla JS), jadi migrasinya kecil. Yang berubah bukan kelayakan, tapi trade-off: kode client-side (countdown 4 pose, drag-and-drop stiker, live video overlay) harus ditulis dan dirawat manual dengan DOM API / event listener, tanpa reactivity otomatis dari Vue. Untuk satu halaman kiosk yang state-nya memang sudah dikenal (bukan aplikasi besar), ini kompleksitas yang bisa dikelola — tapi kalau di kemudian hari fitur ini berkembang (mis. lebih banyak bingkai interaktif, animasi kompleks), migrasi ke Alpine.js akan lebih murah daripada tetap vanilla penuh, karena Alpine tidak menambah build step baru.1.2 Stack FinalFramework: Laravel 13 (routing, Eloquent, queue, scheduler, validation, rate limiting bawaan).Halaman kiosk & publik: Blade templates murni (routes/web.php), tanpa Inertia.Interaktivitas klien: JavaScript vanilla ES modules (resources/js/photobooth/*.js), di-bundle dengan Vite bawaan Laravel (tanpa plugin Vue/React).Database: MySQL (sesuai default Laravel + kemudahan hosting bersama tim).Storage foto: Disk s3 (S3-compatible, mis. MinIO) untuk produksi; disk public untuk development lokal — sesuai NFR-5 PRD produk.QR code: Package simplesoftwareio/simple-qrcode (generate di server, dikirim sebagai data URL/SVG ke Blade — tidak perlu library JS tambahan di klien).Image processing (opsional): Intervention/Image, untuk kompresi ukuran file di server sebelum disimpan permanen.Catatan: Rendah — ini pilihan tim, bukan fakta yang bisa diverifikasi. Package QR dan image processing di atas adalah yang paling umum dipakai di ekosistem Laravel saat ini sepengetahuan saya, tapi versi/status maintenance-nya perlu dicek langsung di Packagist sebelum composer require, karena saya tidak melakukan pengecekan real-time di dokumen ini.2. Alur Frontend per Langkah (Teknis)Satu halaman session.blade.php menampung seluruh langkah (pilih bingkai → capture → stiker → preview → QR); JS yang mengatur langkah mana yang terlihat, mengikuti pola show/hide section yang sudah ada di prototipe.5.1 state.jsSatu objek state modul-scope yang jadi single source of truth untuk sesi saat ini, supaya modul lain (camera, compose, stickers, upload) tidak saling menyimpan state ganda:export const sessionState = {  step: 'frame',        // frame | capture | stickers | preview | qr  frameId: null,  poses: [],             // 4 data URL hasil capture  compositeCanvas: null,  stickers: [],           // [{ id, type, x, y, rotation }]  uploadStatus: 'idle',   // idle | uploading | success | error  photoSlug: null,};5.2 camera.js — FR-1, FR-3getUserMedia({video: true}); tangani NotAllowedError dengan pesan jelas + tombol fallback “mode tanpa kamera” untuk testing (FR-1).Fungsi runCaptureSequence(): loop 4x — tampilkan overlay countdown 3 detik (setInterval), lalu drawImage video ke canvas sementara, simpan sebagai data URL ke sessionState.poses, jeda singkat, ulangi. Update indikator progres 1–4 di DOM langsung setiap iterasi (FR-3).5.3 compose.js — FR-4composePhotoStrip(poses, frameId): gambar 4 pose ke satu <canvas> vertikal, load asset bingkai (PNG overlay) sesuai frameId, tempel watermark brand + tanggal di canvas.Target performa: di bawah 1 detik, seluruhnya di sisi klien (NFR-1) — tidak ada round-trip ke server pada tahap ini.5.4 stickers.js — FR-5Stiker dirender sebagai elemen <img>/<div> yang diposisikan absolute di atas canvas preview (bukan digambar langsung ke canvas), supaya bisa di-drag bebas.Drag ditangani dengan pointerdown/pointermove/pointerup (Pointer Events API, bukan library eksternal) — update x, y di sessionState.stickers saat drag berlangsung.Saat “Simpan Foto” ditekan, stiker (posisi final) di-drawImage ke compositeCanvas supaya hasil akhir jadi satu gambar flat sebelum dikirim ke backend.5.5 upload.js — FR-6, FR-7, NFR-2compositeCanvas.toBlob() → FormData → fetch POST /api/photos dengan header X-PSD-Unit.Retry otomatis 2–3x dengan backoff singkat bila fetch gagal/timeout; setiap percobaan mengubah sessionState.uploadStatus dan teks di layar (“sedang mengunggah…” / “gagal, coba lagi”) sesuai NFR-2.Response sukses berisi { slug, download_url, qr_svg } — qr_svg dirender langsung dari server (lihat §6), JS tinggal menyisipkannya ke DOM, tidak perlu generate QR di klien.5.6 gallery.js — FR-8fetch GET /api/photos?psd_unit_id=... saat halaman galeri dibuka, render grid thumbnail, klik = modal lihat ukuran penuh.5.7 Navigasi kembali — FR-9Tombol “Kembali ke Menu” eksplisit di setiap langkah; tidak ada setTimeout yang otomatis redirect, supaya tidak memotong proses pengguna scan QR.6. Kontrak APIPOST /api/photosRequest (multipart/form-data):photo: <file, image/png|image/jpeg, max 8MB>frame_id: stringpsd_unit_id: stringResponse 201:{  "slug": "aZ3kQ9mN",  "download_url": "https://wakafair-siginjai.id/foto/aZ3kQ9mN",  "qr_svg": "<svg ...>...</svg>"}Response 422 (validasi gagal) / 429 (rate limit) mengikuti format error standar Laravel.GET /api/photos?psd_unit_id=...&page=1{  "data": [    { "id": 12, "slug": "aZ3kQ9mN", "thumbnail_url": "...", "created_at": "..." }  ],  "meta": { "current_page": 1, "last_page": 3 }}GET /foto/{slug}Bukan JSON — mengembalikan halaman Blade publik (photo-show.blade.php) berisi <img> foto + tombol unduh. 404 Blade custom jika slug tidak ditemukan atau status ≠ active (NFR-3: tidak boleh membocorkan daftar semua foto).7. Job, Scheduler & Slug Generation7.1 Slug unik (FR-11)PhotoSlugGenerator men-generate random string (mis. Str::random(8), base62, hindari karakter ambigu 0/O/I/l), dicek unik terhadap tabel photos sebelum dipakai. Bukan auto-increment murni, supaya tidak bisa ditebak-tebak lewat URL.7.2 Pembersihan otomatis (FR-14)Command php artisan photos:cleanup: cari photos where expires_at <= now() and status = active, hapus file dari storage lalu set status = deleted (soft, bukan hard delete baris, supaya metadata untuk audit tetap ada). Didaftarkan di routes/console.php / Kernel schedule() untuk jalan harian via cron (schedule:run).Perlu konfirmasi sebelum rilis: Rentang retensi 7 hari masih berstatus “sementara” di PRD produk (belum dikonfirmasi pemilik produk) — nilai ini disarankan dibuat sebagai config value (config('photobooth.retention_days')), bukan angka hardcode, supaya bisa diubah tanpa deploy ulang kode.8. KeamananRate limiting: middleware throttle pada route POST /api/photos (mis. RateLimiter::for('uploads', ...) di AppServiceProvider) — NFR-3.Validasi file: StorePhotoRequest membatasi mime type (image/png, image/jpeg), ukuran maksimum, dan menolak file yang bukan gambar valid (bukan hanya cek ekstensi).Endpoint publik /foto/{slug} tidak pernah menampilkan daftar/indeks foto lain — hanya bisa diakses lewat slug spesifik.HTTPS wajib aktif di domain publik (lihat pertanyaan terbuka kepemilikan domain di PRD produk §8) sebelum QR code dipakai di lapangan.CSRF: endpoint kiosk (halaman Blade + JS di origin sendiri) tetap pakai token CSRF Laravel standar; tidak perlu API token terpisah karena bukan API publik.9. Rencana Pengujian10.1 Feature test (Laravel, backend)POST /api/photos dengan file valid → 201, slug ter-generate unik, baris photos tersimpan, file ada di disk fake.POST /api/photos dengan file bukan gambar / melebihi ukuran → 422.POST /api/photos melebihi rate limit → 429.GET /foto/{slug} untuk slug valid & status active → 200, menampilkan foto.GET /foto/{slug} untuk slug tidak ada / status deleted/expired → 404, tidak membocorkan info lain.GET /api/photos?psd_unit_id=X hanya mengembalikan foto milik unit X (isolasi antar unit).Command photos:cleanup menghapus file & mengubah status foto yang sudah expires_at terlewati, tidak menyentuh yang belum.10.2 Pengujian manual di sisi klien (tidak otomatis, dilakukan di hardware kiosk sungguhan)Izin kamera ditolak → pesan jelas + fallback tampil, sesuai FR-1.4 pose berurutan dengan countdown — pastikan tidak ada frame yang terlewat/blank di browser kiosk yang dipakai unit PSD.Drag stiker terasa responsif di layar sentuh (bukan hanya mouse) — titik risiko terbesar dari pendekatan vanilla JS, wajib diuji di perangkat sungguhan sebelum rollout.Upload gagal (matikan jaringan sesaat) → retry & pesan status tampil sesuai NFR-2.Scan QR dari HP → halaman publik terbuka & foto bisa diunduh.11.
